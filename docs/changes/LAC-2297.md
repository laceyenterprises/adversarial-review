# LAC-2297 — Retire a canonically fenced legacy repair epoch

## Summary

The native repair reservation keeps custody across failed, filtered and
point-in-time absence reads. LAC-2297 adds an HQ-owner operation that can
retire one unscoped legacy merge-rescue reservation with the exact committed
enqueue fence from [Agent OS #11350](https://github.com/laceyenterprises/agent-os/pull/11350).

## Interface changes

`bin/retire-legacy-repair.mjs --apply` takes the same repo, PR, full base head,
epoch, owner key and original handoff round as the producer. It reads the
durable receipt through the canonical Postgres read-only runtime, verifies the
enqueue guards and checks the owner family for launches and retries. The
producer's evidence builder verifies the current open PR, exact reservation
and original submitter under AR's intent and retry-ledger locks. The operation
records `canonical-enqueue-fenced` and the receipt on the terminal epoch.
Competing custody, queued work and all spend and refund history stay intact.

Final comment-round remediation preserves safe producer refusal codes, strips
private path suffixes, distinguishes reader timeouts, and accepts historical
repository aliases in strict dispatch reads without releasing live custody.
The runbook records the maximum 65-second ledger-write stall and the private
producer API dependency. The stored epoch adds optional `enqueueFenceReceipt` and the terminal reason
`canonical-enqueue-fenced`. No lifecycle enum changes.
Merge-lease JSON parse failures already propagate; regression coverage pins
that refusal instead of adding a redundant strict option.

The existing dispatch-read grant authorizes an observation of launch state or
absence. The HQ-owner boundary already authorizes the canonical proof read, so
the command needs no additional entitlement. The sibling watcher, reserve,
next-action and TTM paths continue to use pending versus bound or terminal
repair custody. The [runbook](../RUNBOOK-ama-closure.md#retire-one-fenced-legacy-repair-reservation-lac-2297)
owns operator acceptance after deployment.

### Second comment-only closeout

The canonical reader accepts both serialized text and an already decoded JSON
receipt. The adapter query retains its parameter binding and complete owner-family
absence checks. Reader safe refusal codes survive unrelated warning lines; all
other stderr remains redacted. Offline regressions cover both receipt shapes and
warning-prefixed/suffixed refusals.

The producer reads the reservation with `node --input-type=module -e READ_EPOCHS`,
calling `readHammerRetryCapLedger` directly. That read does not acquire the
retry-ledger mutation flock or the closer-intent lock. The shared repository
read lock remains compatible with the outer shared read lock; it is not a nested
exclusive writer. The held-lock deployment regression below validates the real
Node read, without any live ledger access.

The operator command intentionally accepts only canonical lowercase repository
selectors and matching canonical ledgers. Historical dispatch aliases remain
supported for competing-custody detection. A noncanonical ledger itself refuses;
no alias-based reservation identity or producer evidence is substituted. This
restriction is explicit in the runbook rather than broadening a recovery boundary.

Rescue independently ran the exact committed fence query through
`open_ledger_for_runtime_readonly` against a qualified disposable PostgreSQL
server upgraded through the complete canonical Alembic chain. The producer
committed a real fence receipt, then the consumer read it with parameter binding
and actual global absence checks; equality passed. The same optional integration
suite passed all three tests, including three real Node reservation reads while
both retirement locks were held and the observation-stable digest check. The
owned server exited cleanly. The earlier minimal-schema fixture was correctly
refused by the normal schema-head guard and is not counted as acceptance.
