# LAC-2347 — Recognize a queued re-review dismissal after terminal remediation

## Summary

HAM withdrawal cleanup treated a native queued re-review dismissal as a
HAMFINAL dismissal. In adversarial-review PR #2056, review 6044130491 was
dismissed on a head move in GitHub event 37162162876. The later terminal
predicate accepted the repaired admission-stall blocker. The separate
optional-chain advisory was disputed, leaving zero admitted blocking
withdrawals. Cleanup still refused the merge.

The cleanup now recognizes this case only for an older applicable review with
a complete blocker list, selected by the exact-head terminal-remediation
trace. It reads the complete GitHub timeline for the target PR and requires a
matching native-bot queued re-review dismissal for that review and judged
head. It rechecks the review and live head before continuing. The event
explains why GitHub already cleared the veto. Finding authority still comes
from the predicate and the live review proof.

The queued re-review watcher produces the dismissal event. The daemon’s
superseded-terminal dismissal and the merge writer retain their existing
proof paths. HAMFINAL continues to revalidate admitted withdrawals on retries.
Standing vetoes still reach the existing merge and branch-protection gates.

Final comment-only remediation accepts either case for the timeline's
`changes_requested` state while rejecting absent, non-string and unrelated
states. The CLI retains its head-match guard: `src/ama/eligibility.mjs`
explicitly sets `headMatch.ok` when terminal remediation validates, including
when the reviewed and current heads differ. Its existing predicate regression
test confirms that contract; the CLI comment now makes the dependency explicit.
The advisory trace simplification was not applied because retaining the
admission checks preserves the existing fail-closed boundary (zero savings).

## Interface changes

The cleanup CLI uses the existing verdict trace and lazily reads the GitHub
issue timeline for a matching candidate. No new CLI flag, store field,
lifecycle state, configuration key, or deployment step is required.
