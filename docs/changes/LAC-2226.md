# LAC-2226

## Summary

Repair ownership reads can use the existing paired project/repository grant
when dispatch records its canonical project at reservation. The reader checks
the reservation key, repository and base head in both the keyed response and
the retry root. A complete terminal chain at the base head permits one
successor under the existing lease, claim and epoch cap. Empty reads retain
custody because the reservation precedes enqueue.

A moved PR head requires a verified produced-head attestation by the
reservation's launch or its retry before the watcher attributes the head to that
repair. An independently published head leaves the reservation and counters
intact.

## Interface changes

`bin/repair-in-place.mjs` accepts the canonical dispatch project as its ninth
positional argument. Use empty strings for the seventh and eighth arguments
when the caller has no native follow-up claim. The reservation persists the
project and uses it with the repository in its keyed read. Older reservations
continue using their exact unscoped key. Replays cannot set or replace stored
scope. `observeRepairOwner` takes the reservation's qualified `repo` for exact
root identity validation.

## Agent OS owner handoff

The source in `cwp_dispatch/dispatch.py` reserves using `ctx.idem` before
provisioning and enqueue. `cwp_dispatch/pr_repair.py` passes the qualified PR
repository and native claim but omits the project. Later,
`dispatch.py` gets `ctx.project_ref` from the provisioned workspace and uses
`ctx.project_ref or ctx.project` in canonical launch lineage. The caller owner
needs to resolve and freeze that identity before reservation, pass it through
`reserve_pr_repair`, and verify that enqueue uses the same project and
repository. If the project is unresolved at reservation, omit it. An explicit
pair still requires the producer's existing matching grant. The caller owner
should also verify that managed repair publication emits the existing produced
attestation for its actual launch and exact PR head.

The installed read for Agent OS #11196 returned `dispatch absence scope
unproven` after session preparation. The follow-up probe sent only the
repository, which the producer refuses for scoped recovery. The persisted
reservation lacks an admission project. Recovering that legacy attempt needs
authoritative evidence of its original admission and a durable fence against
any late enqueue for its key. A new caller argument supplies neither for an
old reservation. The current operator-published head needs its own independent
provenance through the ordinary review path once custody is lawfully released.
