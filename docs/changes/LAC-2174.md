# LAC-2174 — bounded history collection throughput

## Summary

Agent OS #10268 at `4e82bfaa39031da9febb10e565016bef8b0ddb0d`
(2 commits, 53 changed files, reported green CI) still exhausted the canonical
90-second history budget after adversarial-review #1753. The existing owner and
next action remain with that PR's normal closure lane/operator; this source repair
does not take custody, preview, re-drive or mutate that PR.

The reader awaited every sibling subtree serially and reconstructed all patches
before discovering whether there was any hammer history to protect against.
Independent directory pairs now run in waves of eight. Complete paginated commit
history is collected first; author-only and classification-only reads avoid tree,
blob and diff work. Hammer decisions still collect every primary/final patch.
Immutable commit pages are reused locally; symbolic comparisons stay live.

Final comment-only remediation stops pagination workers from claiming additional
pages after a page read fails, while awaiting already active reads before
returning the failure. A later call can retry the failed page normally. Directory
waves append children iteratively so wide trees cannot exceed JavaScript's
function argument limit. These fixes retain the same live-unblock scope and
`LAC-2174-history-throughput` scenario; the companion Agent OS requirements-ledger
update remains outside this repository's dispatch scope.

## Interface changes

`createHistoryReader().commitHistory(comparePath)` returns validated complete
paginated commit history without file evidence. It does **not** set
`filesComplete`. The collector propagates this optional capability through its
cancellation and persistent-history wrappers; injected legacy readers still work.
No store shape, config, gate, deadline, quota, authorization, terminal lifecycle or
cancellation ownership changes. No CI jobs or checks added.

## Offline reproduction and measurements

`test/history-read-throughput.test.mjs` generates immutable synthetic SHA-addressed
objects for 2 commits and 53 files in independent directories. It uses sanitized
names/content only; it is a shape reproduction, **not** a captured production
history or a measurement of GitHub latency. The dispatch supplied no immutable
production history/latency trace. No production reads or credential access were
used to fill that gap.

A full comparison executes one commit-page request, 108 tree requests, 106 blob
requests and 53 local diffs, retaining all 53 exact patches. Peak concurrent tree
requests is 16. Under the explicitly modeled 2 seconds per API request, excluding
local work and preflight, the former depth-first schedule costs 124 seconds:
one metadata wave + one root pair + 53 directory pairs + seven blob waves.
The new schedule costs 32 seconds: one metadata wave + one root pair + seven
directory waves + seven blob waves. Request volume is unchanged for a required
full proof; directory serialization is removed. These modeled values are
deterministic, not a promise that every production transport fits the budget.
A controlled transport also runs both schedules against the production reader's
monotonic deadline: two-tree admission reproduces the legacy serial request
schedule and returns `HISTORY_READ_TIMEOUT` at exactly 90,000 virtual milliseconds
after 88 tree requests, before blobs. Sixteen-tree admission completes in 32,000
virtual milliseconds, with 1 compare wave, 8 tree waves and 7 blob waves. This
executes the reader and real local git diffs rather than sleeping for 90 seconds.
The final isolated run measured 403.84ms local wall time for the full comparison;
that host timing is separate from the deterministic API latency model.

The author-only collector fixture executes one compare projection and one live
PR read, with zero tree/blob/diff work. Its private nonexistent runtime root
disables durable cache writes/reuse. Eager reconstruction would spend 216 API
requests and 53 diffs on the same classification before dropping its file data;
the new path uses two API requests and zero diffs. The durable-cache path still
performs live metadata preflight and review provenance reads. A hammer fixture requires both full 53-file snapshots
before approval. Malformed commit pagination and truncated trees refuse evidence;
a stalled parallel tree read still times out. Existing regressions pin the exact
90,000ms whole-collection cap, transport retries, quota deferral, independent
in-flight cancellation and immutable-cache reuse.

The stable v2 regression scenario is `LAC-2174-history-throughput`: cold 2-commit,
53-path immutable evidence must avoid sibling directory serialization and avoid
patch reads for author-only classification, while hammer decisions require full
author evidence. This is a narrow v1 live-unblock repair under `src/ama/FREEZE.md`;
no new owner or authority is introduced. The companion Agent OS requirements
ledger is outside this repository's dispatch scope; this source PR carries the
scenario and evidence for its owner's capture.
